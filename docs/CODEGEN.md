# Generated code

ImForge exports ordinary Dear ImGui C++. This page covers what you get, where you can edit it
and how your edits get back into the project. The exact rules are in
[SPEC.md](SPEC.md#code-generation).

## Files

For a project with panels `MainMenu` and `Settings`, `Ctrl+E` writes these into
`codegen.outputDir`:

| File | Contents |
|---|---|
| `MainMenu.h` / `MainMenu.cpp` | `MainMenuState` struct, `DrawMainMenu(...)`, handler functions, locked blocks |
| `Settings.h` / `Settings.cpp` | same for the second panel |
| `imforge_components.h/.cpp` | one function per component definition |
| `imforge_theme_<Name>.h` | `ApplyTheme_<Name>(ImGuiStyle&)` per theme |
| `imforge_styles.h` | push/pop helpers for style classes |
| `imforge_fonts.h` | `LoadFonts(ImGuiIO&)` and one `Font_<Name>()` accessor per font, returning `ImFont*&` |
| `imforge_animations.h` | the project's custom animations as static keyframe tables, when it has any |
| `imforge_reflect.h` | `IMFORGE_REFLECT` tables for your binding types (dev builds) |
| `imforge_dev.h` | registers handlers and locked blocks with the live interpreter (dev builds) |

With `splitHeader: false` each panel is a single header with `inline` functions. The output is
deterministic: the same project always gives byte-identical files.

## What a panel looks like

Each file starts with a one-line "Generated by ImForge" banner, left out here.

```cpp
// @imb:file panel=MainMenu schema=1
#include "MainMenu.h"
#include <cfloat>
// @imb:user id=includes
// @imb:end id=includes
namespace ui {

static void MainMenu_btn_play_OnClick(MainMenuState& state, Player& player, Settings& cfg) {
    // @imb:user id=btn_play.onClick
    // @imb:end id=btn_play.onClick
}

void DrawMainMenu(MainMenuState& state, Player& player, Settings& cfg) {
    const float imb_s = ImGui::GetFontSize() / 13.0f; (void)imb_s;
    // @imb:begin id=window h=9f8e7d6c
    ImGui::SetNextWindowSize(ImVec2(520 * imb_s, 380 * imb_s), ImGuiCond_FirstUseEver);
    if (ImGui::Begin("Main Menu", &state.open, ImGuiWindowFlags_NoCollapse)) {
        // @imb:begin id=btn_play h=11223344
        if (cfg.esp.enabled) {
            if (ImGui::Button("Play", ImVec2(-FLT_MIN, 0))) {
                cfg.esp.enabled = !cfg.esp.enabled;
                MainMenu_btn_play_OnClick(state, player, cfg);
            }
        }
        // @imb:end id=btn_play
    }
    ImGui::End();
    // @imb:end id=window
}
}
```

Panel parameters become reference parameters and bindings become direct member access
(`&player.health`), so there's no reflection or lookup at run time. Panel state variables live
in `<Panel>State`, a plain struct; you own the instance. `visibleIf` turns into an `if`,
`enabledIf` into `BeginDisabled`/`EndDisabled` (or the pre-1.86 equivalent). Style overrides
become matched `PushStyleColor`/`PushStyleVar` pairs and style classes become
`Style_<class>_Push()/Pop()` helpers. Animations and effects call `imb::` functions from
`imb_runtime.h`; shader blur calls `imb::fx::Blur` inside `#ifdef IMB_FX_AVAILABLE`.

## Motions

A node with motions gets a static binding table and a `BeginMotion`/`EndMotion` scope around
its code:

```cpp
static const imb::MotionBinding imb_m_pop[] = {
    {imb::presets::ZoomIn(), imb::Trigger::Enter, 1.0f, 0.0f, -1, 0.0f},
    {imb::presets::Lift(), imb::Trigger::Hover, 0.5f, 0.0f, -1, 0.0f},
};
const ImGuiID imb_mid_pop = ImGui::GetID("pop##m");
if (imb::BeginMotion(imb_mid_pop, imb_m_pop, 2, imb::MotionOptions())) {
    ImGui::Button("Pop");
    imb::EndMotion();
}
```

On a `Window`, `Popup`, `Modal`, `Tab` or `Menu` the scope goes inside, around the content.
If the node has a `visibleIf`, the condition goes into `MotionOptions::visible` instead of an
`if`, so an exit motion can still play after it turns false. Children of a staggered container
get their `stagger_index` the same way. An event with a motion's `on` set calls
`imb::TriggerMotion(id, ...)` next to its actions and handler, and `Text`/`SeparatorText` with
a text reveal motion format into a buffer and cut it with a small `ImbTextReveal` helper that
the generator writes into the file.

Presets come from `imb_motion_presets.h` (`imb::presets::ZoomIn()` and so on). Custom project
animations go into `imforge_animations.h` as `imforge_anim::<Name>()` accessors over static
keyframe tables, plus an `imforge_anim::RegisterAnimations()` that the generated panel draw
calls once, so `imb::FindAnim` knows them by name too. Unknown preset names are skipped with a
warning in Diagnostics.

`imb_motion.h` and `imb_motion_presets.h` are only included when a panel uses motions, and
export then copies them next to the generated code along with `imb_runtime.h`. With the
animations feature turned off in Project Settings no motion code is written at all. The
runtime side is described in [MOTION.md](MOTION.md).

## Markers

| Marker | What it is | Can you edit it? |
|---|---|---|
| `// @imb:begin id=X h=HASH` ... `// @imb:end id=X` | code generated for node `X`; `h` hashes the block body | literal edits are merged back, other edits become conflicts |
| `// @imb:user id=S` ... `// @imb:end id=S` | your code, in a slot the generator never writes | yes, kept as is |
| `// @imb:locked id=X h=HASH` ... `// @imb:end id=X` | a block you own entirely (a `Code` node or a node you locked) | yes, kept as is; previewed in the builder through live attach |

There are user slots for `includes`, `header_extra`, `file_top`, `before_draw`, `after_draw`
and one per event handler body.

## Round-trip

When you export over an existing file:

1. Every `@imb:user` and `@imb:locked` body is carried into the fresh output.
2. Each `@imb:begin` block whose hash no longer matches is tokenized and compared with the
   freshly generated block. If only literals differ (strings, numbers, flag identifiers), the
   new values are written back into the node's properties and the builder shows what changed.
3. Anything else is a conflict. The Conflicts panel shows your code next to the generated code.
   *Keep my code* locks the node and keeps your block as its body; *regenerate* throws your
   edit away.

Nothing gets overwritten without you seeing it.

## Options

Under project settings, Codegen:

| Option | Values | Effect |
|---|---|---|
| `cppStandard` | 14, 17, 20 | the standard your app builds with; generated code sticks to C++14 (an `a::b` namespace becomes nested blocks), so this only ends up in the CMake snippet. `imforge_reflect.h` and live attach need C++17 |
| `namespace` | string | wraps everything; empty for none |
| `splitHeader` | bool | header + source, or a single header |
| `functionCase` / `variableCase` | `pascal`, `camel`, `snake` | naming of generated identifiers only |
| `indent` / `useTabs` | int / bool | formatting |
| `markers` | bool | turn markers off for a one-shot export (no round-trip after that) |
| `dpiMode` | `none`, `fontSize`, `variable` | no scaling, `GetFontSize()/baseFontSize`, or an explicit `float imb_scale` parameter |
| `baseFontSize` | number | the font size the design was made at |
| `stdString` | bool | `std::string` bindings use `misc/cpp/imgui_stdlib.h`; otherwise `char[N]` buffers |
| `runtimeHeader` | string | include name for `imb_runtime.h` |

## Version guards

Generated code targets the ImGui version picked in the wizard. Where the API differs between
supported versions (`SeparatorText`, `BeginChild` flags, `BeginDisabled`, tab color names, font
loading), the generator emits `#if IMGUI_VERSION_NUM >= ...` blocks, so one file compiles
against everything from 1.85 up. See [VERSION_MATRIX.md](VERSION_MATRIX.md).
